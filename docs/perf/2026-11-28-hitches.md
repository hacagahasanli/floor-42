# PEWFIELD long-frame investigation, 2026-11-28

Branch `portal-build`. Question: what causes the 216 / 316 / 283 ms frames in 3 of 4 solo 1P matches (`docs/playtest/2026-11-28-old-vs-new.md`, R4) and the 400 ms frame in release QA (`docs/release-qa/2026-11-28-crazygames.md`, item 11)?

## Answer in four lines
1. **I could not reproduce a frame over 100 ms inside a match on a quiet machine.** 22 solo matches on production builds with the real GPU: the worst in-match frame was 100 ms (once), then 83 ms (once), then 50 ms (a few times).
2. **I did reproduce 216 ms (in a fight) and 500 ms (behind the VS doors of a rematch) when three Chromium WebGL sessions ran at the same time** (`con-a`, `con-b`). The playtest and QA ran with other browsers and servers around, so GPU/CPU contention on the test machine is the most likely source of the reported hitches. That is a likely cause, not a proven one: I cannot see what else ran during the playtest.
3. **The suspects in the brief are not the cause of any hitch I measured.** Every in-match hitch had 0 to 6 ms of script in its Long Animation Frame entry, so the time was not spent in JS. Canvas-texture drawing, material creation and sound decode are main-thread JS. The one hitch I traced was an 83 ms GPU-process raster task.
4. **There is one real, repeatable hitch pair per page load, and it is not in the fight.** About 2.05 s before `gameplayStart` (behind the VS doors) the first match builds the game: a 66 to 86 ms frame, then a 50 to 66 ms first frame. It occurs in every first match (all 24 sessions measured) and in no rematch.

## Environment
- Machine: the dev Mac (Darwin 25.5, Apple Silicon), Chromium 1255 with ANGLE Metal (real GPU), launch args as in `docs/collab/shots/colour-balance/impl2/capture.mjs`. 1280x720 unless noted, fresh profile per session, no CPU or network throttling.
- Code: detached git worktrees of `ad2c20b` (portal-build HEAD when I started) and `fce5403` (the playtested build), both under the session scratchpad. I did not edit `src/` or `dist/` in the repo and ran no `npm run build*` there. The other engineer's tree moved while I worked, so "HEAD" below means `ad2c20b`. Between `fce5403` and `ad2c20b`, `src/game` differs only in awards, copy, one rig line and `sfx.ts` (audio gate).
- Builds: `vite build` inside the worktrees, served with `python3 -m http.server` (3297 = HEAD, 3296 = `fce5403`). One dev server, `npx vite --config vite.portal.config.ts --port 3298 --strictPort` from the HEAD worktree, for one traced run.
- Player: the playtest's scripted masher (A/D alternate, Space every 140 ms, W every ~0.4 s). Not a human.

**Dev server vs real.** The dev server serves unbundled modules and dev-mode React. I used it only for the one full trace (`dev-1`). All counts below come from production builds. A full-category trace of one match is 400 to 500 MB and slows the page, so most runs have no trace.

## The suspects in the brief
- **First-use shader compile.** `prewarm()` compiles the scene up front, and no in-match frame had compile-sized script. The only compile-sized cost is #2 (66 to 86 ms), which is the prewarm itself. Limit: I did not log each trait event against the frame log, so a one-off trait material compile under 50 ms would not show as a long frame here.
- **Trait callout and damage-number canvas textures.** `buildCalloutArt()` draws all eight canvases once. No in-match hitch had script over 6 ms, so canvas drawing is not in them. A GPU texture upload on first use would show as render or GPU time (like #6 and #7), so I cannot exclude it for those two.
- **First sound decode / AudioContext.** In the probe the AudioContext was created at `performance.now()` 400 ms and was `running` at 421 ms (`dev-1.json` `audio`), before the menu. Nothing audio-related sits near a long frame.
- **Fonts.** Loaded before the menu.
- **GC.** Not measured directly. No hitch had a GC-sized script slice.
- **Machine contention.** Reproduced (#4, #5).

## Smallest fixes and expected effect
Recommendations from the evidence. I changed nothing in `src/`, so none is measured as fixed.

1. **Cut the once-per-load build cost behind the VS doors (#2, #3, #4).** Smallest: in `prewarm()` use `renderer.compileAsync` instead of `renderer.compile`, and build rigs only for the two fighters in the match instead of all of `CHARACTERS` (`game.ts` ~1522). Expected: the single 66 to 86 ms frame spreads over several frames. Check: 5 runs of `an.mjs`, look for `LoAF -2.1`. Alternative: create the game while the menu is up, so the doors play over a built scene (bigger change). Player-visible effect: a smoother door animation, and no 500 ms stall under load. It does not touch the fight.
2. **Check the +2.2 s mark (#5, #6).** A/B: a build with `FightStamps` hidden (or its layer promoted), 10 uncontended matches, then one traced contended run. If the frames at +2.2 s vanish, keep the key strip's DOM change off the large layer. Two observations only.
3. **Re-run the playtest alone before changing game code for R4.** Run `session.mjs` for both builds one at a time with nothing else open. If 216 / 316 / 283 ms do not come back, R4 was the test rig. If they do, trace with the light category set (about 75 MB per match) and read `win.mjs` around each gap.
4. **Add a `long-animation-frame` observer to the game behind `?debug`**, so the next playtest records script attribution without a trace.

## Limits
- 22 uncontended and 6 contended matches. One 100 ms frame in 22 matches is too few to rank #6 to #9.
- Only #6 has a trace, and it is from the dev server. No trace of a prod in-match hitch.
- Not run: 907x510 uncontended, 2P, CPU throttling. A slow phone will lengthen #2 and #3.
- Full traces (`scratchpad/hitch/out/*.trace.json`, up to 510 MB) live in the session scratchpad and may be cleaned up. Scripts and JSON summaries are in `docs/perf/2026-11-28-hitches/`.
- The playtest ran while `portal-build` moved, so I cannot confirm which exact build produced its numbers. I tested `fce5403` and HEAD.
